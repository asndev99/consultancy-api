# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands
- Run dev server (auto-restart on change): `pnpm dev` (or `node --watch src/app.js`)
- Create/apply a migration: `npx prisma migrate dev` — **do not run this or `prisma db push` without explicit user approval** (see Database rules below)
- API docs: served at `/docs` (Swagger UI) from `docs/openapi.yml`
- There is currently no test suite (`pnpm test` is a stub) and no lint/format config in the repo.


## Architecture

Express 5 API using Clean/Layered Architecture. Request flow for every feature is:

```
routes → middleware (auth/role/validation) → controller → usecase(s) → repository → prisma
```

- **`src/presentation/routes/*.route.js`** — Express routers. Each route wires `authMiddleware` → `verifyRole(...)` → `validateBody(schema)` → controller function, in that order. Roles come from `UserRoles` in `src/shared/application.constants.js`.
- **`src/presentation/controllers/*.controller.js`** — thin HTTP adapters. They pull data from `req`, call a usecase, and return the standard envelope `{ code, data, message }`. All controller bodies are wrapped in try/catch that calls `next(error)` — no error handling logic lives here.
- **`src/presentation/schema/<feature>/index.js`** — AJV JSON Schemas (`ajv` + `ajv-formats` + `ajv-errors`) keyed by name (e.g. `CreateBranchSchema`), consumed by `validateBody()` in `src/middleware/validate.payload.middleware.js`.
- **`src/usecases/<feature>/*.usecase.js`** — business logic, one file per operation, aggregated into a `<Feature>UseCases` object via that feature's `index.js` and imported as a namespace (e.g. `BranchUseCases.CreateBranchUseCase(...)`). Usecases receive `req` (for `req.user`, the authenticated actor) plus explicit params, and orchestrate one or more repositories. Cross-repository invariants (e.g. checking a business exists before creating a branch under it) are enforced here, not in repositories.

- **`src/Infra/db/repositories/<feature>/index.js`** — wraps the raw repo functions in a `Proxy` that logs every call (`console.log("[<Feature> Repository] calling ...")`) before delegating. Usecases always import the `index.js` default export, never `repo.js` directly, to keep this logging in place.
- **`src/Infra/db/prisma.client.js`** — single shared `PrismaClient` instance (via `@prisma/adapter-pg`), imported by every `repo.js`.

Other conventions worth knowing:

- Soft deletes: most models have `isActive`/`isDeleted`/`deletedAt`/`deletedBy` rather than hard deletes; repositories generally filter on `isDeleted: false` and "delete" usecases just update these flags.
- Multi-tenancy: most rows carry a `businessId` (and often `branchId`) used to scope queries. A `null`/absent `businessId` on `req.user` means a Super Admin, which several repo functions treat as "not scoped to one business" — check for that pattern (`...(businessId != null ? { businessId } : {})`) before assuming a query is always tenant-scoped.
- Audit fields: `createdBy`/`updatedBy`/`deletedBy` are set from `req.user.id` in usecases, not defaulted in the DB.
- Codes/identifiers (branch code, business code, employee code, student code) are generated by helpers in `src/shared/utils.js`, not by the database.

## Project rules (from `.cursorrules`)

- Routes must live in `src/presentation/routes/`, controllers in `src/presentation/controllers/`, DB models/schemas in `prisma/`. New features must follow the existing route → controller → usecase → repository layering.
- File naming: routes `*.route.js`, controllers `*.controller.js`, services `*.service.js`.
- **Do not change/add/delete Prisma schema fields or models without explicit user consent, and do not run `prisma migrate`/`prisma db push` without explicit approval.**
- **After adding, changing, or removing any endpoint, update `docs/openapi.yml` in the same change so it stays in sync with the implementation.**
